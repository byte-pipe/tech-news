# Harness engineering: leveraging Codex in an agent‑first world

## Overview
- Over five months the team built an internal beta product **without a single line of manually‑written code**; all code, tests, CI, docs, and tooling were generated by Codex.
- The effort produced roughly **one million lines of code**, ~1,500 pull requests, and daily usage by internal power users, achieved in about **1/10 of the time** it would have taken to code by hand.
- The experiment focused on **maximizing human time and attention** by shifting engineers from writing code to designing environments, specifying intent, and creating feedback loops for Codex agents.

## Starting from an empty repository
- First commit (Aug 2025) was a scaffold generated by Codex CLI using GPT‑5 and a few templates.
- The repository’s structure, CI, formatting, package manager, and even the initial `AGENTS.md` were all produced by Codex.
- After five months the repo contains ~1 M lines of code across application logic, infrastructure, documentation, and internal utilities, with an average throughput of **3.5 PRs per engineer per day**.

## Redefining the engineer’s role
- Engineers now work on **systems, scaffolding, and leverage** rather than hand‑coding.
- Progress depends on **clarifying missing capabilities** and making them legible and enforceable for the agent.
- Interaction is primarily through **prompts**: engineers describe tasks, run the agent, and let it open and iterate on pull requests.
- Review is increasingly **agent‑to‑agent**; human review is optional and reserved for critical cases.

## Making the application legible to Codex
- To overcome the QA bottleneck, UI, logs, and metrics were exposed directly to Codex.
- The app can be booted per Git worktree, allowing Codex to launch an instance for each change.
- Integrated Chrome DevTools Protocol and custom skills enable Codex to capture DOM snapshots, screenshots, and navigation for bug reproduction and validation.
- A local, ephemeral observability stack provides logs (via LogQL) and metrics (via PromQL) to agents, enabling prompts like “ensure startup < 800 ms” or “no span exceeds 2 s”.

## Repository knowledge as the system of record
- A monolithic `AGENTS.md` proved ineffective: it consumed context, became stale, and was hard to verify.
- The solution is a **layered knowledge base**:
  - A concise `AGENTS.md` (~100 lines) acts as a **map** with pointers.
  - Detailed documentation lives in a structured `docs/` directory (design docs, execution plans, generated schemas, product specs, references, and dedicated files for design, frontend, plans, product sense, quality, reliability, security).
- This layout keeps context small, ensures freshness, and allows mechanical checks of coverage and ownership.

## Key takeaways
- **Human effort shifts** from writing code to curating environments, prompts, and agent capabilities.
- Providing **direct observability and UI access** to agents dramatically expands what they can validate autonomously.
- A **hierarchical documentation strategy** (map + deep sources) preserves context efficiency and knowledge freshness.
- The experiment demonstrates that with well‑designed scaffolding, **agents can deliver large‑scale software** while freeing human engineers to focus on higher‑level design and strategy.
